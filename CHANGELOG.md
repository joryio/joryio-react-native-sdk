# Changelog

## 1.4.0 - 2026-11-18

Fixed (1.4.0-beta.13), inherited from the native SDKs: more than 100 flag exposures read before one flush are sent as several requests of at most 100 instead of only the first 100. Nothing changes in the bridge.

Fixed (1.4.0-beta.13), inherited from the native SDKs (iOS and Android 1.4.0-beta.13): a flag exposure batch whose request failed (no answer, a 5xx, a 408 or a 429) goes to the native SDK's persisted write outbox with the same `idempotencyKey` and is sent again from there, also after a relaunch; its "already sent" mark is stored only once the server takes it - beta.12 stored it before the request and never retried, so a dropped connection lost the exposure for the session. Wiping the data, a withdrawn consent and an opt-out discard the waiting batches. Nothing changes in the bridge.

Fixed (1.4.0-beta.12), inherited from the native SDKs (iOS and Android 1.4.0-beta.12): flag exposures are sent once per person, flag and variant per session across an app relaunch - the native SDKs keep the session's sent marks on the device and clear them on `reset()` and `identify()` of a different user. Nothing changes in the bridge.

Fixed (1.4.0-beta.12), inherited from the native SDKs (iOS and Android 1.4.0-beta.12): on Android the first flags, placements or cards request after the app had been idle could fail at once and never reach the server (a 1.4.0-beta.11 regression); on both platforms a placements or cards request that got no answer no longer holds the next one back for 30 s, only 3 s; and every flag exposures batch carries an `idempotencyKey`, so the server records a batch sent twice once. New constants `PLACEMENT_RETRY_AFTER_FAILURE_SECONDS` and `CARD_RETRY_AFTER_FAILURE_SECONDS` (3) mirror the native ones. Nothing else changes in the bridge.

Fixed (1.4.0-beta.11), inherited from the native SDKs (iOS and Android 1.4.0-beta.11): on Android, `identify()` of a different user no longer carries the previous user's attributes into the new user's flags and in-app requests; flag exposures are no longer counted twice when a connection drops; and at most 20 Show when re-checks run after an outage of the event queue, on both platforms. The bridge holds no attributes of its own, so nothing changes in the bridge.

Fixed (1.4.0-beta.10), inherited from the native SDKs (iOS and Android 1.4.0-beta.10): on Android a whole-number JS value (`track('x', { n: 3 })`, `setAttributes({ seats: 3 })`) reached the server as `3.0`, because React Native hands every JS number to Android as a Double; it now goes as `3`, as on iOS. And on both platforms, past 20 waiting Show when re-checks the oldest tracked is the one dropped. Nothing changes in the bridge: it already passed the values through unchanged.

Added (1.4.0-beta.9): "Show when" for placement campaigns (Joryio BACKLOG D465), inherited from the native SDKs (iOS and Android 1.4.0-beta.9), which build the placements request and hold an item until its moment: after N foreground seconds on the screen (the last `trackScreen`), or once an event was tracked in this visit (the SDK then re-checks at once, after the event has left the queue, carrying it as `recheckEvent`). A held item is not in `getPlacements` or `onPlacementsUpdated` and `<JoryioPlacement>` does not draw it; at its moment `onPlacementsUpdated` fires with it. The bridge builds no request of its own and passes the native answer through - pinned by a test. `SHOW_WHEN_KINDS` is exported with the same name and values as on every Joryio SDK. A held-out answer's `markDisplayed()` before its moment is ignored natively and `onPlacementsUpdated` fires at the moment; deferred control exposures are reported natively. `scroll` / `exit` are web-only and never shown in an app. There is no capability flag: placements exist only in the 1.4.0 betas, so an older beta (1.4.0-beta.8 and earlier) receives such a campaign and shows it as soon as the screen loads. Web adds `scroll` / `exit` and Web personalization (page edits).

Fixed (1.4.0-beta.6): a beta reports its own version. The release build writes the beta (`1.4.0-beta.6`) into `SDK_VERSION` of the published package, which the bridge sends as `X-Joryio-SDK-Wrapper-Version`; before, every beta said `1.4.0`, so betas could not be told apart in the workspace's SDK versions. The native SDKs underneath (the `joryio-ios-sdk` Swift package and `io.joryio:joryio-android-ui` at the same beta) report the beta in `X-Joryio-SDK-Version` too. The same fix on web, iOS, Android and Unity.

Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `onCardsUpdated`, `onPlacementsUpdated` and `onFlagsUpdated` return a `JoryioSubscription` (new exported type): `cancel()` stops the updates - the same type name and method on iOS, Android, web and Unity (`JoryioSubscription.Cancel()`). It can still be called, `sub()` being `sub.cancel()`, so code that called the returned function keeps working; cancelling twice is harmless. Content cards: `<JoryioCardFeed />`'s `onDeepLink(url, card)` receives the whole `Card` (it was the card id), and `onRender(feed)` receives the whole `CardFeed` (it was `{ cardCount, unreadCount }`), as on iOS, Android and web. Both native view managers send the card's and the feed's `toJson()`, the same JSON as `getCards`. The iOS bridge imports the SDK-internal `attachCardFeedListener` as SPI. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Added: `<JoryioPlacement>` draws an item's recommended products through the native view (Joryio BACKLOG D444) - props `showProducts` (default true), `productButtonText`, `productCardWidth`, forwarded by both view managers. A tap reports `clicked` with elementId `product:<id>`. New exports `PLACEMENT_PRODUCT_ELEMENT_PREFIX`, `PLACEMENT_PRODUCT_CARD_WIDTH`, `placementProductElementId`.

Added: the `time_on_screen` in-app trigger (Joryio BACKLOG D444 follow-up) works through the native iOS and Android SDKs: `Joryio.trackScreen(name)` starts the screen's clock there, and a campaign with the trigger shows after that many foreground seconds on the screen (or any screen). No JavaScript API change; needs the native SDK versions that add it.

Added: `Joryio.setLinkHandler((link) => boolean | Promise<boolean>)` / `clearLinkHandler()` (work before `initialize()`): every link the native SDK is about to open - an in-app message button or link, a `<JoryioPlacement />` button, a `<JoryioCardFeed />` tap, an iOS push tap - reaches JS first as a `JoryioLink` (`url`, `source`: `in_app` / `placement` / `card` / `push`, `campaignId`, `placementKey`, `itemId`, `cardId`, `isAppDeepLink`). Return true to take it over, false for the native behaviour without a handler; a Promise decides later. Both bridges take the link at once (event `JoryioLink`, at most 32 waiting) and JS answers with `completeLink`. Refused schemes never reach JS. `onDeepLink` props keep receiving app deep links, after the handler declines. New config option `forwardUniversalLinks` (iOS only, default false; ignored on Android, which routes verified App Links itself) - see the iOS SDK. The same names and source values on all five SDKs.

Added: content cards and the inbox (Joryio BACKLOG D444 Phase 3, docs/PLACEMENTS_PLAN.md section 11) - a persistent feed per person, filled from card campaigns and the journey step "Add card". `<JoryioCardFeed />` is the native iOS `CardFeedViewController` / Android `CardFeedView` (new view managers `JoryioCardFeedView` on both bridges): a plain scrolling list with image, title, body, optional button, a "Pinned" marker, an unread dot and a dismiss control, "No messages yet" when empty (`emptyText`, `pinnedLabel`, `dismissLabel`, `unreadLabel`), in the system theme; it reports `viewed` then `read` after half a card was on screen for a second, `clicked` on a tap and `dismissed` on the x, opens http(s) links natively, hands app deep links to `onDeepLink(url, card)` and never opens any other scheme. Data first: `Joryio.getCards({ cursor? })` resolving `CardFeed { cards, unreadCount, nextCursor, stateScope }` (each `Card`: `id, campaignId, variantId, title, body, imageUrl, buttonText, url, pinned, createdAt, expiresAt, read, clicked`), `getUnreadCardCount()` (a Promise over the native cache - every React Native read crosses the bridge - never a network call), `markCardViewed` / `markCardRead` / `markCardClicked` / `dismissCard` (a card or its id), `refreshCards()`, `onCardsUpdated(cb)` (returns a `JoryioSubscription`: `cancel()`, also callable); exported `CARD_MIN_REFRESH_SECONDS` (30) and `CARD_FEED_TTL_SECONDS` (300). The native SDKs fetch, cache, rate-limit, keep an anonymous visitor's state and report; every report goes back to the native card object the bridge handed out, which drops it after an identify / reset. Apps with their own push messaging handler call `refreshCards()` on a `jry_sync: "cards"` data message. The same names and wire values on all five SDKs.

Added: placements (Joryio BACKLOG D444, docs/PLACEMENTS_PLAN.md). `<JoryioPlacement placementKey="home_hero" />` is the native iOS / Android `PlacementView` (new view managers `JoryioPlacementView` on both bridges): it sizes itself to what it draws (0 when collapsed), and `deep_link` buttons with an app link (`myapp://cart`, the shared `isAppDeepLink` rule, exported) go to `onDeepLink`; an http(s) link is opened by the SDK, any other scheme (javascript:, data:, intent:, ...) is refused. Data first: `Joryio.getPlacements(keys)`, `refreshPlacements(keys?)`, `onPlacementsUpdated(cb)` (returns a `JoryioSubscription`: `cancel()`, also callable), `item.markDisplayed()` / `markClicked(elementId?)` / `markDismissed()`, `placement.markDisplayed()`; exported `PLACEMENT_VIEWABLE_FRACTION` (0.5) and `PLACEMENT_MIN_REFRESH_SECONDS` (30). The native SDKs fetch, cache, rate-limit, measure viewability and report; every mark call goes back to the native object, which drops it after an identify / reset. Apps with their own push messaging handler call `refreshPlacements()` on a `jry_sync: "placements"` data message. The same names and wire values on all five SDKs.

Added: feature flags and remote config (Joryio BACKLOG D446), routed to the native iOS and Android SDKs, which hold the answer and log exposures. `getFlag(key, defaultValue)`, `getBoolFlag`, `getStringFlag`, `getNumberFlag`, `getJsonFlag` resolve with the value Joryio decided for this person, or your default before the first answer, for a flag Joryio did not send, for a value of another type, or without tracking consent (a getter called before `initialize()` resolves once it has run). `getAllFlags()` (logs no exposure), `refreshFlags()` and `onFlagsUpdated(callback)` (returns a `JoryioSubscription`: `cancel()`, also callable; one native subscription, event `JoryioFlagsUpdated`). Both bridges pass every argument - the key and the default - to the native getter. The same names and wire values on all five SDKs.

Added: the app's React Native package version reaches the dashboard (BACKLOG D427). `initialize()` hands `SDK_VERSION` (now exported) to the native SDK, which sends `X-Joryio-SDK-Wrapper: react-native` and `X-Joryio-SDK-Wrapper-Version: <version>` on every request next to its own `X-Joryio-SDK` (`android` / `ios`) and `X-Joryio-SDK-Version`. Settings > Apps shows the oldest version each app ran in the last 7 days and when a newer SDK is out. Not an app option: the bridge sets it on every `initialize()`. The same wire names on all five SDKs.

Added: `resetTo(anonymousId)`, bound on both bridges to the native `resetTo` (the native SDK checks the id) - everything `reset()` does, then the anonymous id you pass instead of a random one, for an app that keeps its own visitor id (BACKLOG D366). The id must be 8 to 255 letters, digits, `.`, `_`, `:` or `-`, must not have the shape of a Joryio profile id (24 lowercase hex) and must not be the user id the SDK holds; a refused id is logged and the call is a plain `reset()` (a random id), so a logout is never skipped. The same name and rule on all five SDKs. No wire changes: the server sees an ordinary anonymous id. Like `reset()`, `resetTo` drops a click-link token the SDK has not sent yet (one held while consent is pending), so the link is never attributed to the next person on the device.

Changed (BACKLOG D366, before any release of resetTo): it also refuses the anonymous id the SDK holds while a user is signed in - that id is tied to the signed-in person's profile, and adopting it would hand their in-app messages, events, form attribution and push subscription to the next person on a shared device (a random id is used instead). `resetTo` returns `Promise<boolean>`: `true` adopted, `false` refused; both bridges resolve the native answer. The same on all five SDKs.

Changed (BACKLOG D366): `resetTo` also refuses the last 20 anonymous ids this device held for a signed-in user when a reset signed them out (stored locally, newest kept; `wipeData()` forgets them) - a random id is used and it answers `false`, the same message and cap on all five SDKs. A `resetTo` held before `initialize()` and discarded before it runs (pushed out of a full hold) now resolves `false` instead of never settling; the native SDKs answer the same way.

Added: `identifyFromLink(url)`, bound on both bridges to the native `identifyFromLink` (the url is passed through unchanged; native reads the token and applies the rules) - click-link identity. Pass the URL from `Linking.getInitialURL()` and `Linking.addEventListener('url', ...)`; when it carries the `jr_t` token a tracked Joryio message link adds, the native SDK sends it to `POST /v1/identify-link`. The server uses it only to attribute this app's session and later events (Session Start, screen views, conversions) to the contact the message was sent to - it never identifies the person: the app's profile does not become the contact and is never merged into it, and nothing set in the app is written to the contact. Only `identify` joins the two. Held before `initialize()` like other data calls. Nothing happens when a user is identified, the person opted out or consent is denied; while consent is pending the token is held in memory and sent on `'granted'`. The same name, parameter, path and body on all five SDKs.

## 1.3.3 - 2026-11-03

Fixed (from the iOS and Android SDKs this bridge uses): an in-app message the native SDK draws counts as displayed only once someone could have seen it. It is shown only on a screen that is in the foreground and not mid-transition or closing, and `in_app.displayed` is reported - and the campaign's frequency cap spent - only after it has been on screen for `IN_APP_DISPLAY_DWELL_MS` (1000 ms) with the app in the foreground. A tap or a close before then counts as seen (displayed first, then the click or dismissal); a message that leaves the screen sooner is not counted and stays eligible. Before, a message drawn during a screen change was counted and could use up its cap unseen.

Added: `IN_APP_DISPLAY_DWELL_MS` is exported. If your app draws in-app messages itself (`onInAppMessage`), report `'displayed'` by the same rule - see `trackInAppImpression`. No bridge or wire changes.

## 1.3.2 - 2026-10-25

Fixed: an app that subscribes with `onInAppMessage` could get its first in-app message drawn by the native SDK. The subscription is held until `initialize()` completes, and the sync native `initialize()` starts could finish first - seen on Android, where clicks and forms on that message then went through native-only paths; the same window existed on iOS. The SDK now always asks native to hold in-app messages at `initialize()`, and ends the hold once `initialize()` has completed and the held calls have run: your listener takes the held message, or, with nobody subscribed, the native SDK draws it. No message is drawn twice or lost.

Added: `holdInAppMessagesForHandler` in the `initialize()` config, for an app that subscribes AFTER `initialize()` has completed (a screen that mounts later): messages ready before the subscription are held for it. `disableInAppMessages()` instead lets the native SDK draw them. The same option, by the same name, on iOS, Android and Unity.

## 1.3.1 - 2026-10-24

Changed: on iOS the bridge now takes the Joryio iOS SDK as a Swift package (`https://github.com/joryio/joryio-ios-sdk.git`, products `Joryio` and `JoryioUI`, pinned to exactly this version) through React Native's `spm_dependency`, instead of the `Joryio` CocoaPods pod. `pod install` works as before; Xcode resolves the package when the app builds.

- Requires React Native 0.75 or newer (the peer dependency is now `>=0.75.0`). On older React Native, `pod install` stops with an error that says so.
- On React Native 0.75-0.86, the Pods project that `pod install` writes could be reported by Xcode as damaged (a duplicated object id in React Native's Swift package support); the bridge applies the fix React Native 0.87 ships.
- On React Native 0.87 and newer, React Native moves the module map of a pod that uses a Swift package and then looks for it under the pod name, which differs from this module's name; the bridge points the app at the moved file (without it the app does not compile: "module map file '.../joryio-react-native/joryio_react_native.modulemap' not found").
- `JORYIO_IOS_SDK_SPM_URL`, set before `pod install`, builds the native SDK from another git URL (or a local path on React Native 0.84+) - for SDK development only.

Added: `maxWidth` on HTML `InAppMessage` objects (modal and slide-up; modal 600 and slide-up 400 when the server sends none), forwarded by both native bridges. If you draw messages yourself with `Joryio.onInAppMessage()`, give your web view min(maxWidth, screen width - your margins) before the content lays out, and measure the height from `document.body` (with `body{display:flow-root}`), not the root element - the root never reports less than the web view's own height, so a message sized from it can grow but never shrink.

Fixed (through the native SDKs, which draw messages when no `onInAppMessage` handler is set): HTML in-app messages did not work on Android since 1.3.0, and native HTML modals and slide-ups could grow but never shrink. See the iOS and Android release notes.

No other JavaScript API changes.
